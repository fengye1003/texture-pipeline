> 每条格式：**症状 → 根因 → 修法 → 判据**。
> 标记 **[实测]** 的都有可复现的数字；标记 **[经验]** 的是工程约定。

## P1 法线强度不是随手给的数，它是物理量 **[实测]**

- **症状**：材质球上砖缝炸成一条条**白边**，法线贴图单看几乎全是平的蓝色（细节看不见）。
- **根因**：法线强度取成了 `模数像素 × 0.9 = 230`。正确含义应是 **高度范围(mm) ÷ 单像素世界尺寸(mm)**：
  ```
  模数 256px ↔ 300mm  ⇒  单像素 1.17mm
  高度范围 5mm（缝深 + 表面起伏）  ⇒  强度 = 5 / 1.17 ≈ 4.3
  ```
  取 230 时，缝口法线倾角高达 **86°（几乎水平）**，等于把倒角做成了悬崖。
- **修法**：按上式算（本仓库 `--bump`，默认 4.5）。
- **判据**：**正常倒角倾角 10°~30°；p99 超过 45° 就是错的。** 本仓库法线平均倾角中位 0.2°、p99 18°、max 20°。

## P2 渲染全黑 = 缓冲区写进了 NaN **[实测]**

- **症状**：软件渲染出来的球是**纯黑**（背景正常），但贴图采样、几何求交都正常。
- **根因**：Node 的 `Buffer` 写入 `NaN` **静默变成 0**，不报错。而 NaN 来自一处类型误用：向量工具 `mul(a, s)` **只支持标量乘**，却被传了数组 ⇒ 环境漫反射整项变 NaN。
- **修法**：确定性排查 —— 给着色函数加 `--debug`，逐项打印中间量，一眼看到 `diffAmb=NaN`；然后补一个逐通道相乘的 `cmul()`。
- **判据**：**数值管线出现"全 0 / 全黑 / 全白"，先怀疑 NaN，再去找"把数组当标量"这类类型误用。**

## P3 无缝化时，补丁缝带越窄越"抹平"（反直觉）**[实测]**

- **直觉**：缝带越窄，改动的内容越少，越不容易看出来。**实测恰好相反。**
- **根因**：泊松无缝克隆要把"补丁边缘与两侧真值"的失配**摊到整个缝带上**。缝带越窄，同样的失配压进越短的距离 ⇒ 梯度越陡 ⇒ 视觉上那条带越"糊"。
- **实测**（水磨石，1070²；指标 = 缝带中心 16px 的高频能量 ÷ 全图同类条带中位数，1.00 = 完全看不出差别）：

  | 缝带宽度 | 16 px | 32 px | **64 px** | 128 px | 256 px |
  |---|---|---|---|---|---|
  | 指标 | 0.671 | 0.734 | **1.000** | 1.185 | 1.113 |
  | 判读 | 明显抹平 | 偏平 | **无差别** | 无抹平，但改动 12% 面积 | 同上，24% |

- **修法**：**缝带取 64px 量级**（本仓库默认），既无可见抹平、改动面积又最小。更窄只会更糊；更宽是白改内容。
- **判据**：补丁后**缝带中心的高频能量不应低于全图中位数的 0.85 倍**。

## P4 指标设计错误：基线被污染，比结论错误更隐蔽 **[实测]**

- **症状**：同一批图，band64 量出 0.934、band128 量出 1.185 —— **自相矛盾**（更宽的缝带反而"更不平"）。
- **根因**：我把"对照区"固定取在 `中线 − 300px`。而**不同缝带宽度下，该位置可能正好落进缝带内部**（128px 与 256px 就会），于是对照区本身也被处理过 ⇒ 分子分母都不可信。
- **修法**：基线改成**全图同类条带的中位数**，并显式排除缝带自身范围。
- **判据**：**任何"对比型"指标，先问一句"基线会不会也被处理影响"**；会 ⇒ 换成全局统计量（中位数/分位数），不要用固定位置对照。

## P5 清除直线缝：四种做法的实测排序 **[实测]**

处理"产品图上自带的缝/网格线"时，依次试过：

| 做法 | 结果 |
|---|---|
| 逐行线性插值 | **横向条纹**（把二维纹理按行插值，行间产生假条纹） |
| 镜像填补 | **对称"蝶形"**（把邻域镜像进缝带，形成肉眼可见的对称图案） |
| 逐行差值扩散 | **"梯子纹"**（把逐行的高频失配也修了进去） |
| **泊松无缝克隆**（∇²f = ∇²patch，Dirichlet 边界取缝外真值） | **干净** ✅ |

- **修法**：用泊松无缝克隆；补丁来源用 **SSD 匹配**（与缝两侧各 3 列最吻合的等宽条）。
- **判据**：补完后**缝带内外的高频能量比 ≥ 0.85**、且**接缝跳变 < 1.6× 内部**。

## P6 色调校准不能用"乘系数"，要用直方图匹配 **[实测]**

- **症状**：按参考照片把材质整体乘 0.55 后，照片看着"对上了"，但材质**发平、没质感**。
- **根因**：乘法是**线性缩放**，它同时把纹理本身的明暗差（对比度）也一起压扁了。
- **修法**：**逐通道直方图匹配** —— 由参考图建 3×256 LUT，把源图的颜色分布整体映射过去（`scripts/build-tone-lut.py`）。中位色对上的同时，对比度保住。
- **判据**：校准后，**p95−p05 的动态范围不应比校准前明显收窄**（本仓库实测：源 48 → 目标 64，未收窄）。

## P7 打光后"缝"不能是黑线 **[实测]**

- **症状**：无缝和几何都对了，但渲染出来缝是**暗线**，而参考实铺照片里缝是**亮线**。
- **根因**：把缝做成了"深沟"（槽底很低 + AO 很强），阴影压过了缝本身的颜色；而真实的抛光细缝**几乎齐平**，主要靠颜色区分。
- **修法**：抬高槽底、削弱 AO（本仓库：槽底 0.30→**0.55**，AO 强度 0.42→**0.22**）。
- **判据**：渲染图的缝区亮度**应高于或接近砖面**，与参考照片的明暗关系一致。

## P8 量细线颜色必须"取芯"，取均值会被抗锯齿带偏 **[实测]**

- **症状**：量缝色时，"局部响应超过阈值的像素取均值"得到 67，参考图 72 —— 看着只差 5，像是没问题。
- **根因**：细线两侧都是**抗锯齿混色像素**，把均值往砖面色拉。真实缝芯其实差 8（98 vs 106）。
- **修法**：**逐行取缝带内最亮的那个像素**，再对整条缝取中位数（`scripts/measure-joint-core.py`）。
- **判据**：**凡是"细结构"（线、缝、描边）的颜色测量，一律取芯不取均值。**

## P9 AI 生图不能直接当"可平铺材质"用 **[实测]**

- **症状**：让生图模型（`gpt-image-2.5`）按提示词出"无缝贴图"，单看很漂亮（照片味甚至比程序化的更足），但一铺就露馅。
- **实测**（1024²，同提示词；判据见 `docs/04-verification.md`）：

  | 指标 | AI 生图 | 程序化生成 |
  |---|---|---|
  | 左右接缝跳变 ÷ 内部 | **1.92×** | **0.18×** |
  | 上下接缝跳变 ÷ 内部 | **2.61×** | 0.23× |
  | 缝间距离散度（越小越规整） | **25.6%**（间距 96/92/78/79/80/90/80/**160**/87） | **0.0%**（256/256/256） |

- **修法**：**要"可平铺材质"走确定性流水线；要"照片质感"再用 AI，且必须人工修接缝。** 两条路线不冲突 —— AI 图可当"质感参考"。
- **判据**：**"能不能平铺"是一个可计算的比值**（接缝跳变 ÷ 内部相邻跳变），**> 1.6 判不合格** —— 不要靠肉眼。

## P10 找缝要用"导数响应"，且阈值单位必须换算（否则静默零检出）**[实测]**

- **症状 A**：用"列均值偏高"找缝，结果被**纹理本身**带偏（石纹、斑点都会抬高列均值）。
- **症状 B**：把亮度归一化到 0–1 之后，阈值仍按 0–255 写 ⇒ **一条缝都检不出，而且脚本"顺利跑完"**（静默失败）。
- **修法**：① 缝是**贯穿全长的直线** ⇒ 用「与 ±gap 处均值之差」的**行/列响应**（`scripts/prepare-stone.mjs` / `make-seamless.mjs`）；② 任何阈值前先确认**数据量纲**（0–1 还是 0–255）。
- **判据**：**处理后必须回读一遍"缝位置是否还有亮线残留"**（本仓库会打印缝带内最大偏差）；检测类代码**必须有一个"我没找到任何目标"时不静默通过的断言**。

## P11 预览缓冲区按错尺寸落盘 ⇒ 花纹全糊 **[实测]**

- **症状**：生成的预览图整片糊掉、还有横向条纹，看起来像"贴图生成错了"。
- **根因**：预览缓冲区是 `1440×1440`，落盘时却用了闭包里的源图尺寸 `1070×1070` ⇒ **行对不齐**，图像被逐行错位重排。
- **修法**：写图函数显式接收 `w/h` 参数，**不要依赖闭包里的全局尺寸**。
- **判据**：**症状是"整片糊 + 周期性条纹"时，先查尺寸/步长，而不是先怀疑算法。**

## P12 脚本别往控制台打 emoji（Windows GBK 代码页）**[实测]**

- **症状**：Python 脚本在最后一行 `print("✅ 全部通过")` 抛 `UnicodeEncodeError: 'gbk' codec can't encode character '\u2705'` —— **前面跑了半天的正确结果全白费**，看起来像"脚本没跑通"。
- **根因**：Windows 控制台默认 GBK 代码页；emoji（`✅❌ℹ️`）与数学符号（`−` U+2212）编不了。**中文正文不受影响**（GBK 编得了）。
- **修法**：面向控制台的输出一律用 **ASCII 标记**（`[OK] / [NG] / [i]`）；markdown 正文照旧可用 emoji。
- **判据**：**脚本的标准输出不出现非 GBK 字符**（emoji、U+2212、U+2139 等）。

## P13 中转站（New API 类）：一把 key 只能属于一个分组 **[实测]**

- **症状**：生图模型直接 `503 No available channel for model ... under group gpt`。
- **根因**：站点把模型按**令牌分组**路由；生图模型单独在 `image` 组，而手上的 key 在 `gpt` / `claude-kiro` 组。**请求侧绕不过去。**
- **修法**：为该组单独建一把令牌；同时把**镜像线路**做成自动降级（主站失败/超时/5xx/429 ⇒ 换镜像重试，同一把 key 通用）。
- **判据**：`/v1/models` 返回的模型清单，**必须与你要用的模型所属分组一致**（用清单反查分组，比看后台配置更可靠）。

## P14 同一段代码写第三遍时，就该抽成共享模块 **[经验]**

- **症状**：PNG 编解码在两个脚本里各一份，改一处忘一处。
- **修法**：本仓库在**第三个需要它的脚本出现时**抽成了 `scripts/lib/png.mjs`；同理，交付对比图脚本也是第三次写时参数化的。
- **判据**：**该不该抽，看的是"会不会再用"，不是"现在写起来烦不烦"**。第二次用就开始回本；但**两次就抽容易把边界抽错**（这也是一种成本）。

## P15 交付目录的结构本身也是交付物 **[经验]**

- 产出、预览、备选混在一层，使用者会在"哪些文件该丢进引擎"上犯迷糊。
- **约定**：产出单独成目录 + 目录内放**规格书**（逐文件通道/色彩空间/导入选项 + 各引擎接法）+ 搬迁后跑一次 **sha256 比对**（防止搬错版本或留陈旧文件）。
